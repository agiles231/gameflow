# Optional manual asset review

After each independently accepted asset delivery, the coordinator records its exact delivered revision in `.gameflow/assets/manual-review.json` and refreshes a dedicated Blender review scene with the newest five current revisions awaiting optional review (or all when fewer than five). Review is enabled by default. This presentation is part of the delivery workflow, but user inspection, approval, and successful Blender presentation are not technical acceptance gates. Silence never prevents `done`, commits, dependency release, or unrelated production. No reminders or approval requests are needed.

Use `scripts/asset_review.py --project PROJECT enqueue --asset-id ID --task-id TASK --revision REVISION --artifact PATH`, relative to the plugin root. `REVISION` must be a content hash of the frozen delivery manifest (including geometry, materials, textures, and import settings), not a mutable filename, timestamp, or provider job ID. `PATH` identifies a preserved, reopenable source/integration artifact with its dependencies. Keep it project-relative when possible. Enqueue only after independent acceptance, before final bookkeeping. Adding a new revision does not erase older records or carry forward an approval. Repeating the same delivery is idempotent. Completion append order determines the latest five; older pending entries remain available and return into the window as newer ones are approved. Superseded revisions remain as history but do not occupy a slot alongside their replacements.

`select` prints the current selection without mutating state. `present --status shown --selection DISPLAYED.json --reason '...'` records that this exact selection was actually opened and framed (`DISPLAYED.json` is an array of `asset_id`/`revision` pairs captured before presentation; the helper rejects a changed selection); `present --status deferred --reason '...'` records a pending refresh when Blender is unavailable, busy, user-controlled, or lacks enough memory. Never claim `shown` from merely preparing a file. Deferred presentation does not fail acceptance or trigger generation retries. Retry once at the next safe delivery/session boundary after checking ownership; do not repeatedly interrupt the user or relaunch Blender. Keep presentation metadata and the queue in the task checkpoint and handoff.

For existing projects, a missing queue is valid; initialize lazily on first delivery/review migration. Backfill known completed asset revisions from durable manifest/evidence in recorded completion order, without regeneration or inventing historical approvals. Explicit user approval already recorded for the exact revision may be migrated; do not infer it from a task's `done` status. Document any unidentifiable historical revision instead of claiming it was queued.

## Blender presentation

Follow blender-production's application ownership checks. Build/reuse a dedicated `GameFlow_Optional_Review` scene/file containing only task-owned review copies in clearly labeled per-asset collections. Labels identify asset ID, source task, and short revision hash. Arrange copies side by side with enough spacing and a usable view of every asset; preserve real scale or clearly label display-only normalization. Load materials/textures, use practical viewport shading, and frame the selection. For standalone texture/material assets, show the delivered surface on a clearly labeled review-only primitive plane; this is presentation, not new production geometry. Nonvisual assets retain their optional review record and use their appropriate inspection/playback route rather than fabricating a Blender preview. Preserve original delivered files and transforms. Do not introduce artistic acceptance checks, render batches, creative repairs, or provider calls to construct this scene.

Reuse a task-owned review instance and unchanged copies after checking current ownership, file identity and displayed revision hashes; refresh changed copies and framing. Open or refresh through discovered Blender tools, or launch a separate instance only if none is safely reusable and launch is supported and safe. Never replace an unrelated file, discard unsaved work, steal an active user's review scene, or close the user's Blender instance. A clean file alone does not establish ownership. If the user is inspecting/editing, or ownership cannot be established, save a separate review file if possible and record `deferred` with its path. Resume automatic refresh only when application ownership is safely available. A UI integration unable to maintain another instance should defer rather than overwrite the existing session.

## User feedback and reopened tasks

Only the user's explicit decision changes review status. Bind feedback to the asset/revision actually shown; resolve ambiguous asset names with the user before changing a task. Use `decide --asset-id ID --revision REVISION --status approved|disapproved --feedback 'user feedback'`. Approval removes only that revision from the pending window. Disapproval records history and requires the coordinator to reopen the original asset task; the helper intentionally does not mutate task/index/manifest state.

On disapproval, record the complaint in the original task, set its task/index state to `blocked` with `execution_mode: interactive`, and state the concrete next interactive step. Mark its asset manifest entry as revision-requested without deleting the last accepted revision. Route it to the next user interaction, not unattended regeneration. Once the user's desired change is sufficiently clear and authorized, move to `executing` with interactive mode retained and work with the user on that revision. Do not invent an approval requirement for later production: after implementing feedback, normal independent verification can accept a replacement and queue it pending again, without manual approval. Explicit user direction to continue unattended can clear the interactive mode.

Keep previously accepted sources and integration artifacts until the replacement is accepted. Inspect manifest/task dependencies and record affected downstream uses. Suspend dependent tasks that require the rejected revision; do not silently invalidate unrelated work or claim prior technical evidence was false. Previously completed downstream work gets a focused follow-up when the replacement actually requires reimport/reverification. If feedback concerns a superseded revision, record it and establish whether the current revision shares the issue before reopening current work. Never downgrade a newer revision based only on stale feedback. Preserve the rejection, attempted revisions, and original acceptance evidence for traceability.

## Queue format

The template is `templates/gameflow/assets/manual-review.json`; the helper validates it without requiring a separate schema dependency. Version 1 contains `enabled`, `window_size: 5`, append-ordered `entries`, and `presentation`. Entries require `asset_id`, `task_id`, `revision`, `artifact`, `completed_at`, `current`, and `status` (`pending`, `approved`, `disapproved`). Decisions also record the user's feedback, decision time, and decision history. Only one revision per asset is current. Unknown extra fields survive helper edits. Queue updates are coordinator-owned; application workers report presentation outcomes back to the coordinator.
