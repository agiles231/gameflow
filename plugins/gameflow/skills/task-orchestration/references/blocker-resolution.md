# Work through a blocker

Use this protocol when work cannot advance, including a blocked task inherited
from an earlier run. Keep the task graph truthful: blocked work may stay `blocked`
while diagnosis or clarification proceeds. Do not mark it ready until its actual
prerequisites are satisfied, or done until independently accepted.

## Diagnose, act, ask, resume

1. Explain the task and exact missing input, failed criterion, tool failure or
   authority conflict. Cite the relevant evidence or policy and explain what it
   prevents. Separate observed facts from assumptions. An old blocked label is
   not proof that the condition still holds.
2. Read the task's inputs, checkpoint, prior decisions and current user authority.
   Trace dependency chains to the earliest unmet prerequisite. Search available
   project files and connected sources before asking for information already there.
   User direction overrides plugin defaults; do not invent a new permission gate.
3. Attempt the smallest useful authorized step toward completion: recover an
   existing result, inspect an input, diagnose a failed check, draft a missing brief,
   test a permitted approach, or prepare a concrete repair plan. Prefer one bounded
   attempt that resolves uncertainty over repeated audits. Reserve task capacity
   and output/application ownership before production work; prerequisite/child work
   uses the same admission rules as other tasks.
4. If a material choice, missing input or extra authority remains, ask a concise,
   actionable question with a recommended route and its scope/cost when known.
   Make the proposed action reviewable first. Distinguish a skill default from an
   explicit user prohibition. Quote/link any rule that actually requires approval.
   Routine reversible choices inside the approved brief need no question.
5. Continue independent eligible work while awaiting a reply. On reply, record the
   decision and resume the affected task in the same run if limits permit; do not
   require another autopilot invocation. Preserve original repair counts, job IDs,
   ownership and reservations. If a new bounded run is needed, state the consumed
   limit and ask for its extension rather than silently resetting it.

## Common recovery routes

| Blocker | Useful attempt and focused follow-up |
| --- | --- |
| Missing supplied asset or motion | Inspect existing deliveries and compatible inputs. Prepare the exact missing-file requirements, then ask for the source/location or a scoped alternative. Input discovery is not production or reactivation; never silently author or integrate motion that the effective policy defers. |
| Missing production brief | Draft a bounded brief from approved direction, including outputs, references and resource limits. Ask only about unresolved choices; do not treat the draft as generation/spending approval. |
| Failed acceptance with no repairs left | Reuse failure evidence, diagnose the cause and propose a changed, bounded repair with checks and cost. Ask for additional attempts explicitly; do not reset counts, relabel the same repair as diagnosis, or create a child to evade the cap. |
| Unavailable provider or editor | Check current capability and recorded jobs. Use a policy-permitted alternate for non-generation work, or prepare exact connection/recovery steps. Never resubmit uncertain paid work or bypass the provider policy. |
| Default policy conflicts with desired repair | Check whether the user already authorized the specific repair. If not, inspect safely and propose exact edits/preservation checks, then ask for the necessary override. A failed simple method does not prove all repairs impossible. |
| Ambiguous ownership, unsafe state or failed commit | Freeze affected writes/new dispatch as required, inspect safely and isolate the conflict. Ask the narrow ownership/recovery question; never overwrite work to manufacture progress. |

For required user verification, follow
[the review setup and Yes/No approval workflow](../../verification/references/user-verification.md).
Open the candidate in the appropriate application before asking for approval;
if presentation fails, resolve that setup blocker first.

## Keep progress real and durable

Record the concrete attempt, result or changed artifact, remaining blocker, pending
question and exact next action in the existing task contract and current handoff.
Use existing checkpoint fields for identities, jobs and consumed repairs; no new
status or second task database is needed. A diagnosis is not implementation, a
clarification request is not approval, and bookkeeping is not task acceptance.

If only user input remains, use the available input mechanism and leave the
question pending while useful work continues. If the interface requires yielding,
give the actionable question and checkpoint so the reply can resume work directly.
Do not repeatedly ask an unanswered question or re-run the same exhausted attempt
without new evidence. Scheduled/unattended runs surface the question once and
checkpoint by their deadline; honor explicit no-contact policies instead. Genuine
limits and unavailable users can prevent completion, but never substitute a generic
blocked report for an attempt to resolve the cause and a concrete path forward.
